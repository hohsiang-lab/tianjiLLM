# Research: Encrypted OpenAI Subscription Credential Persistence

## R-001: Storage Shape - Reuse CredentialTable

**Decision**: Reuse existing `CredentialTable` without schema migration for the initial implementation plan.

**Rationale**: Repo schema `004_credentials.up.sql` already contains the required three-part shape:

- `credential_type TEXT NOT NULL DEFAULT 'api_key'`
- `credential_value TEXT NOT NULL`
- `credential_info JSONB NOT NULL DEFAULT '{}'`

This exactly matches HO-1176's split between credential type, encrypted token bundle, and safe metadata.

**Alternatives considered**:

- New `OpenAISubscriptionCredentialTable`: rejected because it duplicates existing credential storage and would require extra migration/rollback without a current schema gap.
- Add dedicated JSONB columns for token metadata: rejected for this slice because `credential_info` already carries non-secret metadata.

## R-002: Encryption - Keep Existing NaCl SecretBox Helper

**Decision**: Continue using `internal/auth.Encrypt` and `internal/auth.Decrypt` for token bundle encryption.

**Rationale**: Existing credential handlers already use this helper for `credential_value`; it uses NaCl SecretBox with a random nonce and stores nonce+ciphertext as base64url. Official `golang.org/x/crypto/nacl/secretbox` docs describe SecretBox as encrypting and authenticating small messages, and state random 24-byte nonces have negligible collision risk.

**Alternatives considered**:

- Add envelope encryption/KMS now: rejected as out of scope for HO-1176 because the repo already has a credential encryption primitive and no Linear requirement names KMS.
- Store JSON in `credential_info`: rejected because tokens are secret and `credential_info` is intended to be readable metadata.

## R-003: Token Bundle Fields

**Decision**: Persist only the required secret bundle fields: `access_token`, `refresh_token`, `expires_at`, `account_id`.

**Rationale**: Linear HO-1176 explicitly names these fields for `credential_value`. Existing HO-1174 `openai.TokenBundle` parses `access_token`, `refresh_token`, `id_token`, `token_type`, `expires_in`, and scope/raw response, but HO-1176 does not require durable `id_token` or raw response storage.

**Alternatives considered**:

- Persist full raw token response: rejected because it increases secret surface and may store fields not needed for refresh/use.
- Persist ID token: rejected for this slice; email/account metadata can live in `credential_info`, and ID token persistence should require explicit scope.

## R-004: Metadata Fields and Redaction

**Decision**: Store only non-secret metadata in `credential_info` and always redact `credential_value` in list/info responses.

**Rationale**: OpenAI Codex docs say credential caches contain access tokens and must be treated like passwords. The OpenAI API overview gives the same principle for API keys: secrets should not be exposed in client-side code or shared. Even encrypted blobs are secret material and should not be returned by default.

**Metadata fields**:

- `email`
- `scopes`
- `status`
- `last_refresh_at`
- `last_error`
- `disabled_reason`

**Alternatives considered**:

- Return encrypted `credential_value` because it is ciphertext: rejected because ciphertext is still credential material and gives attackers offline material.
- Omit metadata entirely: rejected because admins need safe status/debug visibility.

## R-005: Refresh Token Rotation

**Decision**: When a successful refresh response returns a new `refresh_token`, overwrite the encrypted stored refresh token; when it omits `refresh_token`, preserve the previous one.

**Rationale**: OpenAI/Codex source persists returned access/id/refresh tokens only when each optional value is present, which preserves existing token fields when absent and writes rotated refresh tokens when present. The OpenAI CI/CD auth guide also documents that Codex refreshes token bundles and writes new tokens back to storage.

**Alternatives considered**:

- Always require a new refresh token: rejected because OAuth refresh responses may omit refresh token when not rotated.
- Always clear refresh token when omitted: rejected because it would break future refreshes.

## R-006: SQL Access

**Decision**: Add a sqlc query for updating `credential_value`, `credential_info`, and `updated_at` in one operation.

**Rationale**: Current `UpdateCredential` only updates `credential_value`. HO-1176 needs token rotation and metadata update to be persisted together. The repo constitution requires all DB queries in `internal/db/queries/*.sql` and generated by sqlc.

**Query shape**:

```sql
-- name: UpdateCredentialValueAndInfo :exec
UPDATE "CredentialTable"
SET credential_value = $2,
    credential_info = $3,
    updated_at = NOW()
WHERE credential_id = $1;
```

Implementation may include `updated_by` if caller identity is available in the surrounding handler.

## R-007: External Verification Notes

- OpenAI Codex auth docs confirm ChatGPT sign-in uses cached credentials and automatic token refresh, and that file-backed credentials contain access tokens and must not be shared.
- OpenAI Codex CI/CD docs confirm refreshed token bundles are written back and should be persisted for future runs.
- OpenAI Codex source shows `TokenData` includes `access_token`, `refresh_token`, and `account_id`, and the refresh persistence path updates optional returned token fields.
- pkg.go.dev SecretBox docs confirm current encryption primitive is appropriate for small authenticated secret payloads.
- Context7 pgx docs confirm JSONB codec support; repo sqlc config already maps JSONB to `[]byte`.
- grep-app GitHub search was attempted but failed with transport content-type error; no public GitHub examples were used from that tool.
